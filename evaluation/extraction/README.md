# 조건 추출 평가셋 (초안)

담당: 김세민 · 관련: FR-002·003·004·018, AI-REQ-04·06 · 이슈 #10 작업 C

채팅 문장에서 조건을 뽑는 AI(LLM)가 얼마나 정확한지 재기 위한 가상 사례 31개다(최소 기준 30개 + DEC-022 사례 1개). `cases.json`에 있다.

> **상태: 초안.** 기대 결과만 있고 실제 실행 결과는 없다. 김영무와 최소 10문장을 함께 검토한 뒤 확정한다. 통과로 표시된 사례는 없다.

## 구성

| 분류 | 개수 | 확인하는 것 |
|---|---|---|
| 기본 추출 | 5 | 지역·시간·이동수단·동행·실내 선호 |
| 강도 분류 | 5 | "꼭·절대"의 HARD 승격, 부정 표현, 예산, 제외 카테고리 |
| 되묻기 | 4 | 지역·시간 누락 시 질문(최대 2개), 시각을 지어내지 않음 |
| 이동제약 | 4 | 휠체어·유모차·부상, "없음"(`[]`)과 미입력(`null`) 구분 |
| 영유아 동반 | 4 | 유모차 자동 적용과 사용자 선택 우선(DEC-002·020), 가족인데 영유아 미언급 시 확인 질문(DEC-022) |
| 미지원 이동수단 | 3 | 스프린트 2 채팅 안내와 수락(DEC-019) |
| 기존 조건 유지 | 3 | 언급하지 않은 기존 조건 보존(DEC-021) |
| 부정·오해 표현 | 3 | "꼭 카페일 필요는 없어요", 인사말, "야외도 괜찮아요" |

## 사례 형식

| 필드 | 의미 |
|---|---|
| `id`, `category`, `requirements`, `decisions` | 사례 ID, 분류, 관련 요구사항·결정 |
| `input` | 사용자 메시지. 전부 `[가상]` |
| `before` | 사전 상태: 가정한 지원 범위(`FINAL`/`SPRINT2`), 빈 프로필에 덮어쓸 값, 확인 대기 항목 |
| `expected.extracted` | 이번 메시지에서 AI가 뽑아야 할 항목(`{value, source, strength}`) |
| `expected.policy` | 추출 뒤 서버 정책(기본값·DEC-019·020)이 적용된 결과 |
| `expected.unchanged`, `mustNot` | 바뀌면 안 되는 항목, 나오면 안 되는 해석 |
| `expected.status`, `questionFields`, `warningCodes` | 응답 상태, 질문 항목, 경고 코드 |
| `result` | 실행 결과. 아래 형식으로 채운다(지금은 모두 `null`) |

`result`에 채울 값: `actual`(실제 응답), `runDate`, `codeRevision`(커밋), `modelVersion`(LLM 이름·버전, 규칙 파서면 `rule-parser`), `verdict`(`PASS`/`FAIL`/`EXCLUDED`), `defectIssue`(결함 이슈 번호).

## 기준 시각과 지원 범위
- 기준 시각은 2026-11-12(목) 10:00 KST다. "토요일"은 11/14, "일요일"은 11/15다.
- `FINAL`은 최종 범위(4개 권역, 도보·대중교통·자차)로, 스프린트 범위 정책이 추출 평가를 가리지 않게 한다. `SPRINT2`는 DEC-019 사례에만 쓴다.

## 채점

| 지표 | 계산 | 목표 |
|---|---|---|
| **필드 정확도** (AI-REQ-04) | 사례마다 9개 프로필 항목 × 31사례. `extracted`에 있는 항목은 `value`·`source`가 같으면 정답, 없는 항목은 USER가 아니면 정답 | 85% 이상 |
| **강도 정확도** (AI-REQ-06) | `extracted`에 있는 항목의 `strength` 일치 비율 | 85% 이상 |
| **되묻기 발생률** (AI-REQ-06) | 지역·시간이 빠진 사례(되묻기 분류)에서 해당 항목 질문이 나온 비율 | 100% |
| **질문 초과** (AI-REQ-06) | 한 응답의 질문이 2개를 넘은 횟수 | 0건 |

- `preferenceTags`는 `keywordsAny`의 단어 중 하나가 들어 있으면 맞은 것으로 본다.
- `acceptable`이 있으면 그 목록의 어느 값이든 정답이다.
- `openQuestion`이 있는 사례는 결정 전까지 해당 부분을 채점에서 뺀다(현재 없음. Q1은 DEC-022로 결정).
- 추출 정확도(`extracted`)와 정책 결과(`policy`·`status`·경고)는 따로 기록한다. 정책 결과는 고정 입력 규칙 검증이라 AI 평가와 분리한다(evaluation/README).

## 실행 대상
- **LLM 추출**이 평가 대상이다. 규칙 파서(AI 실패 시 대체 경로, #17)는 일부 표현(예산, 제외, "다쳤어요")을 일부러 확인 필요로 넘기므로 점수가 낮게 나오는 것이 정상이다. 규칙 파서 결과는 참고로만 기록한다.
- 김영무의 정책 사례(`contracts/policy-cases.json`, PR #13)와 같은 틀(사전 상태 → 메시지 → 추출 → 응답)을 따르므로 테스트 입력으로 재사용할 수 있다.

## 실행 도구와 참고 결과 (2026-11-13)

`run.py --provider rules --output results/rules-2026-11-13.json`은 키 없이 규칙 대체 경로를 측정한다. 저장소 루트의 `.venv/Scripts/python.exe evaluation/extraction/run.py`로 실행한다. 실제 모델은 `--provider gemini`와 로컬 `backend/.env`의 GEMINI_API_KEY·GEMINI_MODEL을 사용한다. 입력 기준 시각은 위 referenceNow를 고정한다. 원본 cases.json과 result:null은 보존하고 별도 보고서를 만든다.

규칙 참고 측정은 234/279(83.87%)이며 LLM 목표 85%의 충족 증거가 아니다. JSON에는 실제 추출·정책 함수 실행 결과, 필드/강도/질문 검사, 모델·코드·실행일·fallback 수를 기록한다. HTTP 검증은 pytest에서 별도로 수행한다. 자연어 mustNot는 수동 검토 대상으로 남기며 자동 검사만 통과한 경우에도 검토 필요를 표시한다. 아직 실제 모델 정확도 측정과 담당자 교차 검토는 수행하지 않았다.

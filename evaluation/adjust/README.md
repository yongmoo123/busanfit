# 수정 요청 평가셋 (초안)

담당: 김세민 · 관련: FR-015, AI-REQ-07, UC-005, AC-007 · 이슈 #39

코스가 나온 뒤 "2번 빼줘" 같은 수정 요청을 AI(LLM)가 얼마나 정확히 해석하는지 재기 위한 가상 사례 20개다. `cases.json`에 있다.

> **상태: 실제 LLM 평가 완료(11/26).** 수정 API 계약(#86)의 `AdjustmentIntent` 형식으로 채점한다. 평가셋 문장·정답은 초안 그대로다.

## 구성
모든 사례는 같은 [가상] 기존 코스(카페 → 미술관 → 음식점 → 공원, 13:00~18:00)를 대상으로 한다.

| 분류 | 개수 | 변경 연산 |
|---|---|---|
| 빼기 | 4 | REMOVE (번호·카테고리·이름으로 대상 지정, 건강 언급 포함) |
| 바꾸기 | 4 | REPLACE (같은 카테고리 / 다른 카테고리 / 종류 미지정) |
| 체류 늘리기 | 3 | EXTEND_STAY (분 지정 / 미지정) |
| 실내로 | 3 | INDOOR (전체 / 특정 장소) |
| 정보 없음 포함 | 2 | INCLUDE_UNKNOWN (직접 요청 / 제안 수락, FR-013) |
| 해석 불가 | 2 | UNCLEAR (모호한 말 / 없는 번호, UC-005 3a) |
| 여러 변경 | 1 | 첫 번째만 적용 + 확인 질문 (DEC-024) |
| 조건 변경 | 1 | PROFILE_CHANGE, 조건 변경 경로로 (DEC-025) |

## 채점
| 지표 | 계산 | 목표 |
|---|---|---|
| **의도 해석 정확도** (AI-REQ-07) | 연산(`op`)·대상(`targets`)·적힌 `params`가 모두 맞은 사례 / 채점 대상 사례 | 80% 이상 |
| 나머지 유지 (AC-007) | 수정 뒤 `unchangedOrders`의 장소·시각이 그대로인지, 체류 연장은 `reschedule`(밀린 장소·불가 판정)이 맞는지 | 위반 0건 (재스케줄링 검증, 해석 점수와 따로 기록) |

- `acceptable`이 있으면 그 목록의 어느 연산이든 정답이다.
- `mustNot`의 해석이 나오면 실패다. 문장형 항목은 사람이 검토한다.
- 채점 대상은 20개 전부다. AD-19는 첫 연산과 확인 질문(`followUp`)이 모두 맞아야 정답이다.
- `result` 형식은 [조건 추출 평가셋](../extraction/README.md)과 같다(`actual`, `runDate`, `codeRevision`, `modelVersion`, `verdict`, `defectIssue`).

## 결정된 규칙
- **여러 변경 (DEC-024):** 말한 순서대로 첫 번째만 적용하고 나머지는 확인 질문. 말없이 버리면 실패.
- **체류 연장 (DEC-027):** 대상 앞 장소는 그대로, 뒤 장소는 장소·순서를 유지한 채 시각만 밀 수 있다. 시간창·영업시간을 넘으면 코스를 바꾸지 않고 이유와 대안을 안내한다.
- **조건 변경 (DEC-025):** "7시까지로 늘려줘"처럼 조건을 바꾸는 말은 연산을 만들지 않고 조건 변경 경로로 보낸 뒤 코스 재생성을 안내.

## 실행
```text
.venv/Scripts/python.exe evaluation/adjust/run.py --output <결과.json>                                  # 규칙 대체 경로(LLM 없음)
.venv/Scripts/python.exe evaluation/adjust/run.py --provider gemini --delay 6 --output <결과.json>       # 실제 Gemini, 무료 티어라 6초 간격
```
- #86의 `AdjustmentInterpreter`에 공통 [가상] 코스 요약을 넣어 **해석(의도)만** 채점한다. 연산 형식은 계약 `AdjustmentIntent`(op·targets·category·minutes·field·followUp)이다.
- 나머지 유지(AC-007)·체류 연장 재배치는 해석기가 아니라 수정 서버가 하므로 여기서 채점하지 않는다. #86의 자동 테스트와 실제 서버 확인(11/26, #93)으로 따로 기록한다.
- **AD-16 제외**: 해석기에 직전 제안 문맥을 넘기는 경로가 없다. 정보 없는 장소 포함 수락은 채팅이 아니라 명시적 동의 화면으로 처리한다(DEC-033, #30).
- `acceptable`은 사례 최상위에 있으며 `expected`의 대안 정답이다.

## 실행 결과

### 2026-11-26 실제 LLM 평가 (`results/gemini-2026-11-26.json`)
- 모델 `gemini-3.5-flash-lite`(DEC-030), 가상 입력, 코드 develop `9a06368`(앱 코드는 #91 병합본 `05011b2`와 같음) + 이 실행기(커밋 전, `workingTreeModified: true`), 사례 사이 6초 간격, 규칙 대체 0건
- **의도 해석 정확도 84.2% (16/19, 목표 80%)**. AD-16을 실패로 넣어 20개로 계산해도 80.0%(16/20)
- 실패 3건
  - AD-04 "다리가 좀 아파서 3번까지만 갈게요": 첫 연산을 `PROFILE_CHANGE(mobility)`로, REMOVE [4]를 followUp으로 냄. 이동제약을 몰래 바꾸지는 않음(조건 변경은 카드로 안내, DEC-025). 순서 규칙(DEC-024) 위반으로 실패 처리
  - AD-06 "미술관 말고 다른 데", AD-08 "조용한 곳으로": 말하지 않은 카테고리(ATTRACTION·OTHER)를 지어냄 → 교체 후보가 그 카테고리로 좁혀짐
- 해석 응답시간: 평균 5.0초, 최대 12.2초(재시도 포함, 로컬)
- 채점기 수정 기록: 처음 실행 때 사례 최상위 `acceptable`을 읽지 못해 AD-18(REMOVE [5] 허용)을 실패로 셌다. 고친 채점기로 같은 실행의 저장된 해석 결과를 다시 채점했다(LLM 재호출 없음, 결과 파일 `rescoredNote`)

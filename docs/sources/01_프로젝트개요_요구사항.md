## 현재 프로젝트
부산핏(BusanFit): **제약 맞춤형 부산 놀거리 코스 추천 서비스**.
사용자의 지역·시간·이동수단·이동제약·예산·선호·동행 조건에 맞는 코스를 실제 부산 데이터로 구성한다.
과거 대화의 진로 탐방·역사 관광·주차 전용 서비스는 초기 아이디어였고, 현재 문서의 구현 주제가 아니다.

LLM은 조건 추출·수정 의도·추천 설명, DB와 규칙 엔진은 장소 선택·시간 계산·검증을 담당한다.
부산 전역 수집을 지향하되 서면·해운대·광안리·남포 중심으로 품질을 검증한다.

## 수업 필수 조건
- LLM 또는 VLM 활용: 이 프로젝트는 LLM 사용, VLM은 범위 밖.
- 부산 관광·문화·생활·교육 등의 실제 DB/API 활용.
- 핵심 기능 최소 3개: 조건 분석, 장소 검색, 코스 생성, 지도 표시 등.
- GitHub 협업, 요구사항·설계·테스트 등 소프트웨어공학 프로세스 수행.
- 데이터 출처 명시, 저작권 및 이용조건 준수.

## 주요 흐름
입력 → 누락 조건 질문(최대 2개) → 조건 카드 확인/수정 → 장소 검색 → 코스 배치·검증 → 지도·타임라인·이유·출처 → 조정 제안.
예약·결제·회원가입·로그인·부산 외 지역·VLM·실시간 영업/혼잡 보장은 제외한다.
영화 일정은 사용자가 고정 일정으로 입력하며 상영시간표 자동 연동은 제외한다.

### 1. 프로젝트 개요

#### 1.1 배경

부산은 바다·문화·음식 등 놀거리가 많지만, 대부분의 코스 추천은 "건강한 성인이 대중교통으로 하루를 통째로 쓴다"는 일반 사용자를 가정한다. 한편 부산교통공사·한국관광공사·부산시는 역사 엘리베이터, 무장애 관광지, 주차장 운영시간 등 실제 제약을 판단할 수 있는 공공데이터를 개방하고 있다.

#### 1.2 문제 정의

휠체어·유모차 이용자, 부상자는 일반 추천 코스를 그대로 따를 수 없다(계단, 긴 도보, 엘리베이터 없는 역).

영화·예약 식당 등 고정 일정이 있으면 그 사이 공백 시간을 어떻게 채울지 스스로 조사해야 한다.

자차/대중교통, 예산, 날씨, 동행자(연인·가족·친구)에 따라 적합한 코스가 달라지지만, 이를 한 번에 반영하는 서비스가 없다.

범용 LLM에 물어보면 존재하지 않거나 폐업한 장소, 실제로 접근할 수 없는 장소를 추천할 수 있다.

#### 1.3 목표

자연어 대화에서 사용자 제약을 구조화하고, 하드/소프트 제약으로 구분한다.

부산 공공데이터에 실제로 존재하는 장소만으로, 하드 제약 위반 0%인 코스를 생성한다.

기본값으로 첫 코스를 빠르게 보여주고, 후속 질문과 대화형 수정으로 사용자가 자연스럽게 코스를 조정하도록 유도한다.

모든 추천 장소에 데이터 출처와 접근성 등급을 표시한다.

### 2. 기존 서비스 대비 차별점

부산핏의 핵심 차별점은 "LLM은 이해와 설명, 계산은 규칙 엔진"이라는 역할 분리로, 제약을 지키는 코스를 재현 가능하게 만든다는 점이다.

| 구분 | 지도 앱 장소 검색 | 여행 일정 앱 | 범용 LLM 챗봇 | 부산핏 |
| --- | --- | --- | --- | --- |
| 자연어 조건 입력 | 키워드 위주 | 수동 편집 | 가능 | 가능 |
| 이동제약(휠체어·유모차·부상) 반영 | 제한적 | 없음 | 불확실 | 하드 제약 필터 |
| 시간창·이동시간 계산 | 경로 단위 | 사용자 몫 | 부정확 | 스케줄러가 계산 |
| 장소 실존 보장 | 보장 | 보장 | 환각 가능 | DB 검증 후 출력 |
| 데이터 출처 표시 | 일부 | 일부 | 없음 | 장소별 표시 |
| 대화형 부분 수정 | 없음 | 없음 | 전체 재생성 | 해당 부분만 재계산 |

단순 LLM 호출만으로 구성된 시스템이 아니라, 제약 추출 → 필터 → 점수화 → 스케줄링 → 검증 → 설명의 다단계 파이프라인으로 동작한다.

### 3. 개발 범위

구현 범위는 비로그인 반응형 웹에서의 제약 분석·코스 생성·대화형 조정이며, AI는 LLM만 사용한다.

#### 3.1 포함

채팅 기반 조건 입력 및 제약 프로필 추출: 시간, 이동능력(자차·대중교통·장애요소), 예산, 선호도(관광·체험·야외활동 등), 날씨, 동행 관계(연인·가족·친구)

하드/소프트 제약 구분 및 기본값 적용

제약 기반 후보 검색, 시간·이동시간을 고려한 코스 생성

코스 타임라인 + 카카오맵 표시, 장소별 추천 이유·출처·접근성 등급

후속 조정 제안(최대 3개) 및 대화형 부분 수정

자차 모드 주차장, 역사 엘리베이터·보관함 등 편의시설 표시

#### 3.2 제외

예약·결제, 회원가입·로그인

실시간 혼잡도, 실시간 영업 여부 보장

영화관 상영시간표 연동(공개 API 없음 → 사용자가 고정 일정으로 직접 입력)

쓰레기통·휴대폰 충전소 안내(부산 공개 데이터 미존재)

이미지 기반 질의(VLM): 향후 확장 항목으로만 기술

부산 외 지역

#### 3.3 지역 범위

부산 전역 데이터를 수집하되, 추천 품질 검증과 시연은 주요 권역(서면, 해운대, 광안리, 남포)에 집중한다.

#### 3.4 향후 확장 가능성

VLM을 활용한 "이런 분위기 장소" 사진 질의

대중교통 경로 API 연동을 통한 이동시간 정밀화

식이 제한(채식·알레르기) 데이터 연동

### 4. 핵심 기능

과제 필수조건(핵심 기능 3개 이상)을 다섯 가지 기능으로 충족한다.

| 번호 | 기능 | 내용 | 과제 예시 대응 |
| --- | --- | --- | --- |
| F1 | 대화형 제약 분석 | LLM이 채팅에서 제약 프로필(JSON)을 추출하고 하드/소프트를 태깅, 필수 정보 누락 시 최대 2개 되물기 | 사용자 맞춤 |
| F2 | 제약 기반 장소 검색 | 공공데이터 DB에서 하드 제약을 만족하는 후보만 조회, 접근성 등급(확인됨/정보 없음/부적합) 부여 | 데이터 검색 |
| F3 | 맞춤 코스 생성 | 소프트 제약 점수화 + 시간창·이동시간·체류시간 기반 스케줄링, 고정 일정 사이 공백 채우기, 검증 후 출력 | 사용자 맞춤 추천 |
| F4 | 지도·동선 시각화 | 타임라인과 카카오맵 동선, 장소 상세·출처, 주변 편의시설(주차장·엘리베이터·보관함) | 지도/위치 연동 |
| F5 | 상호작용 코스 조정 | 기본값으로 첫 코스 생성 후 조정 제안 칩 표시, 칩·자연어 수정 시 해당 부분만 재계산 | 사용자 맞춤 |

#### 4.1 기본값 정책

| 항목 | 기본값 | 후속 질문 예시 |
| --- | --- | --- |
| 카페 체류 | 60분 | "카페에 더 오래 있을 예정이신가요?" |
| 식사 체류 | 70분 | "식사는 여유있게 하실건가요?" |
| 전시·문화시설 체류 | 시설별 관람소요시간, 없으면 60분 | "전시는 얼마나 보실 예정인가요?" |
| 접근성 정보 없는 장소 | 이동제약 모드에서 제외 | "정보가 없는 장소도 포함해서 다시 만들어드릴까요?" |
| 미입력 이동수단 | 대중교통 | "자차로 이동하시나요?" |
| 미입력 예산 | 제한 없음, 가격대 보통 | "예산 상한이 있으신가요?" |

화면에는 기본값이 적용된 항목을 표시하고, 코스 생성 후 기본값 적용 항목·정보 없음으로 제외된 장소·날씨 리스크 순으로 조정 제안을 띄운다.

### 5. 활용 데이터 및 출처·이용조건

모든 데이터는 공공데이터포털(data.go.kr) 등 공개 출처에서 활용신청 후 사용하며, 화면에 출처를 표기한다. 세부 이용허락 범위(공공누리 유형)는 활용신청 시 데이터별로 재확인한다.

| 데이터 | 제공기관 | 활용 목적 | 비고 |

### 6. 기술 스택 및 LLM 선정

프론트엔드는 React, 백엔드는 FastAPI, LLM은 개발 단계 Gemini Flash 무료 티어 후 시연 단계 유료 소형 모델로 전환한다.

| 영역 | 선택 | 이유 |
| --- | --- | --- |
| 프론트엔드 | React(또는 Next.js) + 카카오맵 JavaScript API | 반응형 웹, 국내 지도 표시 |
| 백엔드 | Python FastAPI | 데이터 처리·LLM 연동 라이브러리 풍부 |
| DB | PostgreSQL(+PostGIS) 또는 SQLite | 좌표 기반 반경 검색 |
| LLM | 개발: Gemini Flash 계열(무료 티어) / 시연·최종: 유료 소형 모델(Claude Haiku 5.5 또는 GPT-5 mini) | 비용 최소화, AIService 추상화로 교체 가능 |
| 협업·배포 | GitHub, GitHub Actions | 과제 필수조건, 자동 빌드·테스트 |

#### 6.1 LLM 비교

| 후보 | 장점 | 단점 |
| --- | --- | --- |
| Gemini Flash 무료 티어 | 결제수단 없이 무료, 만료 없음 | 분당 요청 제한 낮음, 무료 티어 입출력이 모델 개선에 사용될 수 있음 |
| Claude Haiku 5.5 | 입력 100만 토큰당 $0.10, 출력 $0.50(10만 토큰 이하 프롬프트) | 결제수단 필요, 2026-10 출시로 자료 적음 |
| GPT-5 mini | 입력 $0.25, 출력 $2.00, 국내 자료 풍부 | 결제수단 필요 |
| 로컬 모델(Ollama 등) | 무료, 데이터 외부 미전송 | 한국어 JSON 추출 품질 불안정, GPU 서버 필요 |

코스 1회당 LLM 호출은 3~5회로, 유료 소형 모델도 학기 전체 비용이 수천 원 수준이다. 부상·장애 정보를 다루므로 무료 티어 개발 중에는 가상 시나리오만 사용한다. (가격은 2026-10 기준, 변동 가능)

### 1. 문서 개요 (Introduction)

#### 1.1 목적 (Purpose)

본 문서는 부산 지역 공공데이터와 LLM을 활용하여, 사용자가 채팅으로 말한 제약(시간, 이동능력, 예산, 선호도, 날씨, 동행 관계)에 맞는 놀거리 코스를 생성하는 웹 서비스 "부산핏"의 소프트웨어 요구사항을 정의한다. 대상 독자는 개발 팀원(PM, 백엔드, 프론트엔드), 담당 교수 및 평가자이며, 본 문서는 설계서(SDD)와 테스트 케이스 작성의 기준으로 사용된다.

#### 1.2 프로젝트 범위 (Scope)

해결하려는 문제: 기존 코스 추천은 일반 사용자를 가정하므로, 휠체어·유모차 이용자나 부상자, 고정 일정이 있는 사용자, 자차/대중교통·예산·동행자에 따라 조건이 다른 사용자는 추천 코스를 그대로 사용하기 어렵다. 범용 LLM은 존재하지 않거나 접근할 수 없는 장소를 추천할 위험도 있다.

핵심 서비스: (1) 대화형 제약 분석: 자연어 입력에서 제약 프로필을 추출하고 하드/소프트 제약으로 구분한다. (2) 제약 기반 장소 검색: 부산 공공데이터 DB에서 하드 제약을 만족하는 장소만 조회한다. (3) 맞춤 코스 생성: 시간·이동시간·체류시간을 계산해 순서와 방문 시각이 정해진 코스를 만든다. (4) 지도·동선 시각화. (5) 상호작용 코스 조정: 기본값으로 첫 코스를 보여준 뒤 조정 제안과 대화형 수정으로 맞춤화한다.

지역 범위: 부산 전역 데이터를 수집하되, 추천 품질 검증과 시연은 주요 권역(서면, 해운대, 광안리, 남포)에 집중한다.

범위 제외: 예약·결제, 회원가입·로그인, 실시간 혼잡도 및 실시간 영업 여부 보장, 영화관 상영시간표 연동(사용자가 고정 일정으로 직접 입력), 쓰레기통·휴대폰 충전소 안내(공개 데이터 미존재), 이미지 기반 질의(VLM, 향후 확장 항목으로만 기술), 부산 외 지역.

#### 1.3 용어 및 약어 (Definitions & Acronyms)

| 용어/약어 | 정의 |
| --- | --- |
| LLM | Large Language Model. 본 시스템에서 제약 추출, 수정 의도 해석, 추천 이유 생성에 사용 |
| VLM | Vision-Language Model. 본 프로젝트 구현 범위에서는 제외하며 향후 확장(사진 기반 장소 질의)으로만 기술 |
| RAG | Retrieval-Augmented Generation. 본 시스템은 DB에서 검색한 후보 장소 정보를 LLM 입력 근거로 제공하여 설명을 생성하는 방식으로 활용 |
| 제약 프로필 | 대화에서 추출한 사용자 조건(시간, 이동수단, 이동제약, 예산, 선호도, 날씨 민감도, 동행 관계)을 항목별 값·강도·출처와 함께 구조화한 JSON 데이터 |
| 하드 제약 | 위반 시 코스가 무의미하거나 위험해지는 조건. 후보 필터로 적용하며 생성 코스는 이를 위반해서는 안 됨 (예: 휠체어 접근, 이용 시간대) |
| 소프트 제약 | 만족도에 영향을 주는 조건. 점수(가중치)로 반영 (예: 분위기, 음식 취향) |
| 앵커(고정 일정) | 사용자가 이미 확정한 일정(예: 14:00 영화). 코스 생성 시 시각을 변경하지 않음 |
| 코스 | 방문 장소의 순서, 방문 시각, 체류시간, 이동시간을 포함한 일정 |

### 2. 전체 설명 (Overall Description)

#### 2.1 제품 관점 (Product Perspective)

부산핏은 독립형 웹 서비스이며, 외부 서비스와 다음과 같이 연동한다. (1) 공공데이터(한국관광공사 TourAPI, 부산교통공사·부산시설공단·공공데이터포털 데이터)는 배치 작업으로 수집하여 자체 DB에 적재한 뒤 조회한다. (2) LLM API는 제약 추출, 수정 의도 해석, 추천 이유 생성에만 사용하며 장소 선택·시간 계산은 자체 규칙 엔진이 수행한다. (3) 카카오맵 API로 지도와 동선을 표시하고, (4) 기상청 단기예보 API로 방문일 날씨를 조회한다.

#### 2.2 대상 사용자 (Target Users)

| 사용자 유형 | 특징 | 주요 목표 | 권한/제약 |
| --- | --- | --- | --- |
| 일반 이용자 (관광객·데이트) | 부산 초행 또는 주말 놀거리를 찾는 사용자, 연인·친구와 방문 | 고정 일정 사이 공백 채우기, 취향에 맞는 코스 추천 | 일반 사용자 (비로그인, 세션 단위 이용) |
| 이동 제약 이용자 | 휠체어·유모차 이용자, 부상자, 고령자 | 계단·장거리 도보 없이 접근 가능한 장소 위주 코스 | 일반 사용자, 건강 관련 입력은 세션 종료 시 폐기 |

#### 2.3 운영 환경 (Operating Environment)

Client: PC Chrome/Edge 최신 버전, 모바일 브라우저(Chrome·Safari, 화면 폭 360px 이상 반응형)

Server: Linux / Docker, Python 3.11 + FastAPI

External AI/API: LLM API(개발 단계 Gemini Flash 계열 무료 티어, 시연 단계 Claude Haiku 5.5 또는 GPT-5 mini 중 선택), 한국관광공사 TourAPI, 공공데이터포털 API, 기상청 단기예보 API, 카카오맵 JavaScript API

Database: PostgreSQL(+PostGIS 공간 검색) — Vector DB는 사용하지 않으며 확장 시 검토

#### 2.4 제약사항 (Constraints)

부산 지역 관련 데이터의 출처 및 이용조건을 명시할 것 — 모든 장소 데이터에 제공기관·데이터명·기준일을 저장하고 화면에 표시한다.

개인정보 수집을 최소화할 것 — 회원가입·로그인을 두지 않으며, 부상·장애 등 건강 관련 입력은 서버 DB에 저장하지 않는다.

LLM/VLM 단순 1회 호출만으로 구성하지 않을 것 — 제약 추출 → 필터 → 점수화 → 스케줄링 → 검증 → 설명 생성의 다단계 파이프라인으로 구성한다.

실제 결제/예약은 범위 밖으로 둔다.

무장애·가격·영업시간 정보는 공공데이터 기준이며 실제와 다를 수 있으므로, 화면에 이를 고지하고 정보가 없는 항목은 "정보 없음"으로 표시한다.

공공 API 호출 한도를 고려하여 장소 데이터는 배치 수집 후 DB에 캐싱하며, 카카오 API 약관에 따라 카카오 장소 데이터는 대량 저장하지 않는다.

LLM 무료 티어는 입력이 모델 개선에 사용될 수 있으므로, 개발 중에는 가상 시나리오만 사용하고 시연 시 유료 API로 전환한다.

API 비용은 팀 자체 부담 범위(학기 전체 수만 원 이내)로 제한한다.

일정 제약: 중간발표 2026-10-27(문서), 최종발표 2026년 12월 중순(구현·시연).

#### 2.5 가정 및 의존성 (Assumptions & Dependencies)

외부 AI API(LLM)와 공공데이터 서비스, 카카오맵·기상청 API가 정상 제공된다고 가정한다.

공공데이터의 장소 좌표·주소는 정확하다고 가정하며, 도시철도 역간 소요시간은 부산교통공사 표준 시각을 사용한다(실제와 차이 가능).

사용자는 방문 날짜·시간대와 출발(또는 활동) 지역을 대화 중에 제공할 수 있다고 가정한다.

장소 간 이동시간은 MVP에서 직선거리 기반 보행시간 추정과 도시철도 역간 소요시간으로 계산하며, 이동제약 모드에서는 보행 속도를 낮춰 적용한다.

LLM은 지정된 JSON 스키마에 맞춰 응답할 수 있다고 가정하며, 스키마 불일치 시 재시도·대체 처리로 대응한다.

## 제안 1. 미지원 이동수단은 422로 거절합니다

### 확정된 내용과 미합의 부분

DEC-001은 스프린트 2에서 WALK만 지원하고 이후 PUBLIC·CAR를 단계적으로 추가하도록 정합니다. 미지원 이동수단도 표현 자체는 추출하되 지원하지 않는다고 안내해야 합니다.

이슈 #6은 값을 유지하면서 warnings로 안내할지, 422 UNSUPPORTED_CONSTRAINT로 거절할지를 미합의로 남겨두었습니다. 현재 계약 §5는 비어 있지 않은 미지원 조건을 HARD/SOFT 모두 422로 거절하도록 규정합니다.

### 권장안

- 요청한 이동수단이 capabilities에 없다면 **422 UNSUPPORTED_CONSTRAINT**를 반환하는 것을 제안합니다.
- USER가 선택한 PUBLIC/CAR를 WALK로 자동 교체하지 않습니다. 값이 없는 경우의 기본값 적용과 명시적 미지원 요청을 구분합니다.
- 요청 전체를 저장하지 않고 기존 프로필·revision·대화 상태·만료 시각을 유지하는 것을 제안합니다.
- 오류 details에는 `field: transport`와 정적인 미지원 사유를 넣고 입력 원문을 복사하지 않습니다.
- 프론트는 편집 중인 선택을 로컬 메모리에 유지하면서 지원 범위를 안내하고, 사용자에게 직접 수정하도록 요청하는 것을 제안합니다. 서버 저장 완료 표시를 하지 않습니다.

| 가상 상황 | 제안 결과 |
|---|---|
| WALK만 지원하는 서버에 CAR/USER 요청 | 422, transport 필드 안내, 상태 변경 없음 |
| 기존 WALK 조건에서 "대중교통으로 바꿔 주세요" 요청 | 422, 기존 WALK 유지. 변경 성공으로 표시하지 않음 |
| 실제 지원 조건이 갖춰진 서버에서 이동수단을 언급하지 않음 | DEC-001의 단계별 기본값 적용. 위 거절 정책과 구분 |

현재 운영 앱은 capabilities가 비어 있으므로 WALK도 활성 조건으로 저장할 수 없습니다. 이 제안은 HAEUNDAE/WALK 활성화를 승인하거나 구현하지 않습니다.

### 대안과 영향

200과 warnings로 미지원 값을 저장하면 프론트에서 표시하기 쉽지만, 저장 가능한 조건과 실제 추천 가능한 조건을 구별하는 추가 상태·생성 차단 규칙이 필요합니다. 현재 계약과 구현을 유지할 수 있는 422 방식을 권장합니다.

- 백엔드: chat/PUT에 동일한 지원 범위 검증과 실패 시 상태 보존 적용.
- 프론트: 422의 필드별 안내 및 사용자가 수정할 때까지 입력 상태 유지. 배진호 검토 필요.
- 계약: PM 확정 후 §4·5에 미입력 기본값과 미지원 명시값의 처리 차이 명시.
- 테스트: 미지원 HARD/SOFT 모두 거절, 기본값으로 자동 대체하지 않음, 실패 후 revision·TTL·기존 조건 유지.

**결정 요청:** 미지원 이동수단은 422로 거절하고 요청 전체를 저장하지 않는 방식에 대한 승인을 요청합니다.

## 제안 2. 사용자 이동제약 선택을 자동 유모차 기본값보다 우선합니다

### 확정된 내용과 미합의 부분

DEC-002는 hasInfant=true이면 STROLLER를 HARD·source=DEFAULT로 자동 적용하고, 사용자가 카드에서 해제할 수 있도록 정합니다. 추가 확인 질문은 하지 않습니다.

현재 계약의 "영유아 동반만으로 유모차를 자동 확정하지 않는다"는 문구는 DEC-002와 충돌하여 갱신 대상입니다. 다만 사용자가 mobility=[]를 명시한 경우 및 해제 후 후속 chat에서 재적용할지는 별도 합의가 필요합니다.

### 권장안

- mobility가 null/UNSET이고 영유아 동반이 확인되면 DEC-002대로 STROLLER/HARD/DEFAULT를 적용하는 것을 제안합니다.
- **mobility.source=USER인 경우 사용자 값을 우선**하는 것을 제안합니다. USER의 []는 제약 없음이라는 명시적 선택으로 유지하고, USER의 비어 있지 않은 목록에도 STROLLER를 자동 추가하지 않습니다.
- 사용자 값이 없는 경우에만 기본값을 적용하여, 필드 전체에 하나만 존재하는 source가 USER와 DEFAULT 혼합 출처를 나타내야 하는 문제를 피하는 안입니다. 이 우선순위 역시 PM 승인이 필요합니다.
- 카드에서 유모차만 해제하면 다른 이동제약은 유지하고 source=USER로 저장하는 것을 제안합니다. 남은 제약이 없으면 []/USER로 저장합니다.
- 관련 없는 후속 메시지나 영유아 재언급으로 사용자가 해제한 유모차를 다시 켜지 않는 것을 제안합니다. 사용자가 이후 유모차 사용을 명시적으로 요청하면 STROLLER를 USER/HARD로 반영합니다.
- 이동제약을 null/UNSET으로 되돌리는 것은 명시적 해제 []/USER와 구분합니다. hasInfant=true가 유지된 상태에서 null/UNSET으로 초기화하면 기본값 적용 대상으로 돌아가는 것을 제안합니다.

| 가상 사전 상태·입력 | 제안 결과 |
|---|---|
| mobility=null/UNSET, 영유아 동반 확인 | [STROLLER]/DEFAULT/HARD |
| mobility=[]/USER, 이후 영유아 동반 언급 | []/USER 유지, 자동 재적용 없음 |
| mobility=[WHEELCHAIR]/USER, 영유아 동반 언급 | 기존 USER 값 유지, STROLLER 자동 추가 없음 |
| mobility=[WHEELCHAIR, STROLLER], 카드에서 STROLLER만 해제 | [WHEELCHAIR]/USER, 기존 필수 강도 유지 |
| 유모차 해제 후 시간만 변경 | 해제 상태 유지 |
| 해제 후 "유모차도 사용합니다" 명시 | 기존 제약을 보존하며 STROLLER를 USER/HARD로 추가 |
| 영유아 동반 상태에서 mobility를 null/UNSET으로 초기화 | STROLLER 기본값 적용 대상으로 복귀 |

영유아 동반을 false로 바꾸는 경우에는 아직 DEFAULT인 자동 유모차만 해제하고, USER가 지정한 제약은 유지하는 방식을 추가 제안합니다. 삭제·재적용은 명시적인 사용자 변경 및 기본값 정책에 따라 처리하며, 해석 실패 때문에 HARD 조건을 삭제하지 않습니다.

### 영향

- 백엔드: chat 병합과 PUT 전체 교체에 같은 기본값 규칙 적용. 실제 이동제약 지원 전에는 정규화된 조건도 미지원 검증으로 거절하며 저장 성공으로 처리하지 않음.
- 프론트: null과 [] 구분, 기본값 배지 및 해제 동작, null 초기화 시 재적용 안내. 배진호 검토 필요.
- 계약: §4 자동 유모차 문구·USER 우선순위·초기화 의미 갱신. 직접 변경 USER 규칙과 DEFAULT 유지/정규화 동작 정리.
- 테스트: 자동 적용·USER [] 우선·기존 제약 보존·해제 후 chat·명시적 재선택·영유아 해제·미지원 시 미저장.

**결정 요청:** USER 값을 DEFAULT보다 우선하고, 해제 상태를 후속 대화에서 유지하는 방식에 대한 승인을 요청합니다. 특히 USER의 비어 있지 않은 목록에도 자동 추가하지 않는 기준을 함께 확인해 주시기 바랍니다.

## 제안 3. 503과 NEEDS_INPUT의 경계를 명시합니다

### 확정된 내용과 추가 확인 사항

DEC-007은 LLM 지연(10초 초과)·스키마 불일치 시 1회 재시도하고 재실패하면 규칙 파서로 대체하도록 정합니다. 불확실한 HARD 판단 항목은 UNSET으로 확인을 요청하고, SOFT에는 기본값을 적용하며 warnings로 대체 처리 사실을 안내합니다. 파서도 지역·시간을 추출하지 못하면 503 AI_UNAVAILABLE을 반환합니다.

추가 확인할 부분은 지역·시간 중 하나만 확보한 경우, 기존 세션 값이 있는 경우, 정상적인 미입력과 대체 파서 실패를 구분하는 기준입니다.

### 권장 판정안

| 처리 상황 | 제안 응답 | 상태 처리 |
|---|---|---|
| LLM이 정상 처리했고 사용자가 지역·시간을 입력하지 않음 | 200 NEEDS_INPUT | 부족한 항목을 최대 2개 질문 |
| LLM 재실패 후 파서 대체, 기존의 유효한 값까지 포함하여 지역·시간 둘 다 확보하지 못함 | 503 AI_UNAVAILABLE | 기존 프로필·revision·대화 상태·TTL 유지, 카드 직접 입력 안내 |
| 대체 경로에서 지역 또는 시간 하나만 확보 | 200 NEEDS_INPUT | 확보한 조건을 검증하고 부족한 항목 질문, 대체 처리 안내 |
| 대체 경로에서 지역·시간 모두 확보 | 일반 검증 결과에 따라 200 또는 422 | 다른 필수 조건 확인과 지원 범위 검증까지 수행 |
| 기존 지역·시간의 변경 의도가 있으나 새 값을 해석하지 못함 | 확인 필요 응답 제안 | 이전 값을 변경 성공 결과처럼 사용하지 않음. 미확인 변경 상태의 계약 표현은 아래 검토 필요 |

여기서 "둘 다 확보하지 못함"은 **지역도 없고 시간도 없는 경우**를 의미하도록 제안합니다. 하나만 부족한 상황은 포함하지 않습니다. 이 표의 200은 유효한 세션·revision·요청 제한·지원 조건 검증을 통과한 경우에 한하며 409·410·422·429 등을 덮어쓰지 않습니다.

LLM 정상 처리에서의 단순 미입력과, LLM 재실패 후 파서 대체에서도 값이 없는 상황을 별도로 취급하는 안입니다. 대체 파서에서 값이 없는 경우에도 원문 자체에 해당 정보가 없었다면 항상 200으로 처리할지에 대해서는 대안 검토가 가능합니다. 입력에 정보가 있었는지를 신뢰할 수 있게 판단하는 추가 기준이 필요하므로, 위 표는 우선 대체 경로의 확보 결과로 판정하는 안을 권장합니다.

### 기존 조건 보존 및 미확인 HARD 처리

- 새 메시지에서 언급하지 않은 기존 값은 유지하고 판정에 포함하는 것을 제안합니다.
- 파서의 UNSET으로 기존 USER/HARD 조건을 덮어쓰지 않습니다. 명시적 변경이 해석되지 않은 경우에는 이전 조건 그대로 생성하지 않고 사용자 확인을 요청합니다.
- 지역·시간이 있어도 이동제약·예산 상한 등 다른 HARD 판단이 미확인이라면, 확인 전 코스 생성을 차단하는 것을 제안합니다.
- 현재 계약은 NEEDS_INPUT을 생성 필수 정보 부족으로 정의하고, profile의 null/UNSET만으로는 단순 미입력과 해석 실패를 구분할 수 없습니다. 따라서 "미확인 변경/미확인 HARD가 남음"을 표현하는 응답·세션 상태와 코스 생성 차단 규칙의 계약 보완이 필요합니다.
- 새 상태 enum이나 필드를 이 문서에서 확정하지 않습니다. 이 방향이 승인되면 최소 변경안을 별도로 제시하고 프론트·백엔드 공동 검토 후 반영하는 것을 제안합니다.

### 영향과 확인 기준

- 백엔드: LLM/파서 처리 출처 구분, 기존 값 병합, 503에서 상태 미변경, 미확인 상태의 생성 차단.
- 프론트: 503 직접 입력 안내, 200의 질문·warnings 처리, 미확인 변경과 저장 성공 구분. 배진호 검토 필요.
- 계약: §7의 503 판정표, 200 확인 대기 상태의 의미 및 필요 시 스키마 변경. SRS·SDD와 같은 기준 적용.
- 테스트: 신규/기존 세션별 지역·시간 확보 조합, 503 상태 보존, 기존 HARD 유지, 미확인 변경 시 생성 차단, 대체 처리 안내.
- 가상 검수 사례: 기존 휠체어 HARD 조건에서 "카페는 빼 주세요" 처리 중 LLM 실패가 발생해도 이동제약을 유지해야 합니다.

**결정 요청:** 위 503 판정표와 기존 값 포함 기준을 승인해 주시기 바랍니다. 미확인 HARD/변경 의도의 확인 대기 및 생성 차단은 계약 보완 방향까지 검토를 요청합니다.

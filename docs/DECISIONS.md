## DEC-001 기본 이동수단
> 2026-11-18 DEC-028로 일부 대체: 제출본은 해운대·서면·광안리·남포 권역 확장(가능 시)과 도보만 지원하고, 대중교통·자차·기본값 PUBLIC 전환은 향후 과제다.

- 날짜: 2026-11-05 · 결정자: 김세민(PM)
- 결정:
  - 최종 기본 이동수단은 **대중교통**(SRS FR-005 유지).
  - 스프린트 2는 **도보(WALK)만 지원**한다. 이 기간 기본값은 WALK(`source=DEFAULT`)로 카드에 표시하고, `capabilities`로 지원 범위를 화면에 알린다.
  - 스프린트 3에 대중교통(PUBLIC)을 추가하면서 기본값을 대중교통으로 바꾼다. 이동수단 값 이름은 계약(`WALK`/`PUBLIC`/`CAR`)을 따른다.
  - 도보(WALK) 검색 반경은 **권역 중심 기준 1.5km**로 하고 설정값으로 관리한다. 데이터 확인 후 조정한다.
  - **자차(CAR)**는 스프린트 3에 대중교통 다음 순서로 추가한다. 주차장 표시(FR-017)와 자차 검색 반경 5km를 함께 묶는다. **스프린트 3 일정이 빠듯하면 가장 먼저 축소**한다.
  - 스프린트 2에서는 자차 표현도 추출하되, `capabilities` 기준 미지원으로 안내한다.
- 이유: 대중교통 모드는 역 정보·역간 소요시간 데이터가 필요해 첫 연결을 늦춘다. 한 권역 안에서는 도보만으로 전체 흐름(채팅→카드→코스→지도)을 먼저 완성할 수 있다.
- 영향: FR-005, FR-007, FR-009
- 반영 위치:
  - [x] SDD 1.4 단계별 지원 범위 신설 (DEC-008과 함께), 자차 지원 시점·축소 우선순위 포함
  - [x] SDD 7.3 검색 반경에 도보 1.5km 추가
  - [x] API 계약 §4 — 기본 이동수단·지원 범위 문구 반영 (#13·#48, 2026-11-18 develop 병합). 일반 capabilities 활성화는 실제 연결 검증 후 별도 진행.

## DEC-005 DB: SQLite
- 날짜: 2026-11-05 · 결정자: 김세민(PM)
- 결정:
  - DB는 **SQLite**를 사용한다. PostgreSQL·PostGIS·Docker DB 컨테이너는 사용하지 않는다.
  - 좌표는 위도·경도 숫자 컬럼(`latitude`, `longitude` REAL)으로 저장한다.
  - 반경 검색은 Repository 안에서 ① 위경도 사각형으로 1차 필터(일반 인덱스) ② 하버사인 거리로 2차 필터 순서로 처리한다.
  - 좌표계 변환(EPSG:5174→WGS84)은 적재 시 `pyproj`로 한 번만 수행한다.
  - JSON 컬럼(`open_hours`, `raw` 등)은 TEXT에 JSON 문자열로 저장한다.
  - 설계 문서의 컬럼 타입은 SQLite 실제 타입(INTEGER, REAL, TEXT)으로 적고, 원래 의미는 설명에 적는다. 예: 불리언 → INTEGER "0/1 불리언", 시각 → TEXT "ISO 8601 시각", JSON → TEXT "JSON 문자열", UUID → TEXT "UUID 문자열".
  - DB 파일은 커밋하지 않는다(.gitignore의 `*.sqlite*`, `*.db`). 누구나 같은 적재 명령으로 재생성할 수 있어야 한다.
  - 코스 엔진은 DB를 직접 호출하지 않고 **PlaceRepository 인터페이스**만 사용한다. 인터페이스는 이찬용·김영무가 스프린트 1 안에 합의한다.
- 이유: 부산 장소 데이터는 수천~1만 건 규모로 예상되어 공간 인덱스의 성능 이점이 없다(전체 탐색도 수 ms). 설치가 필요 없어 팀 전원의 로컬 환경·CI·배포가 단순해진다. 기존 ADR-007에 대안으로 기록되어 있던 안이다.
- 트레이드오프: 공간 질의를 직접 구현해야 함(약 30줄), 쓰기 동시성이 약함(읽기 전용 서비스라 영향 없음), 데이터 갱신은 새 DB 파일 생성 후 교체 방식.
- 영향: FR-007, FR-017, FR-020, NFR-001
- 반영 위치:
  - [x] SRS 2.3 운영 환경 Database 줄
  - [x] SDD 1.3 Performance("PostGIS 공간 인덱스" 문구), 3 COMP-10 의존성, 5.1 ER 캡션, 10.1 배포(db 컨테이너 제거), 12 추적표 NFR-001
  - [x] SDD 2.2 — ADR-007을 "대체됨(ADR-008, DEC-005)"으로 표시하고 ADR-008(SQLite) 추가
  - [x] SDD 5.2 — 모든 타입을 SQLite 타입으로 변경(GEOGRAPHY→latitude·longitude REAL, JSONB→TEXT 등), 원래 의미는 설명 칸에
  - [x] SDD 그림 2-1(아키텍처)·5-1(ER)·10-1(배포)을 Mermaid로 다시 그림 — 원본 `docs/diagrams/`, PNG `docs/images/`

## DEC-006 건강 정보의 LLM 전달 범위
- 날짜: 2026-11-05 · 결정자: 김세민(PM)
- 결정:
  - **사용자가 쓴 말을 해석하는 호출**(조건 추출, 수정 의도 해석)은 사용자 원문 전달을 허용한다(원문 없이는 해석할 수 없음).
  - **시스템이 만든 데이터를 넘기는 호출**(코스 요약, 추천 이유 생성)에는 건강 정보를 범주값(wheelchair, stroller, injury 등)으로만 넣는다. 수정 의도 해석 때 메시지와 함께 보내는 코스 요약도 범주값만 쓴다.
  - 개발 중에는 가상 시나리오만 입력한다. 시연은 입력을 학습에 사용하지 않는 유료 API로 진행한다.
  - 원문·프롬프트·응답의 건강 정보는 로그에 남기지 않는다.
- 이유: SRS AI-REQ-03·SDD 9장의 "범주값으로만 전달"은 사용자 원문을 해석해야 하는 호출(조건 추출, 수정 의도 해석)과 동시에 성립할 수 없다.

## DEC-007 LLM 실패 처리
- 날짜: 2026-11-05 · 결정자: 김세민(PM)

## DEC-015 무장애 정보 연결과 이동제약 판정
- 날짜: 2026-11-09 · 결정자: 김세민(PM) · 계기: 이슈 #7 질문 7, 정할 것 3
- 결정:
  - **연결**: 장소 기본 정보와 무장애 정보는 원본 ID(`source_place_id`)로 짝짓는다. 짝이 없으면 `accessibility` 행을 만들지 않고 API에서 `UNKNOWN`으로 내보낸다. 해운대 표본으로 두 서비스의 ID 일치를 확인하고 매칭률을 보고한다.
  - **항목값**(휠체어·유모차·엘리베이터·장애인 화장실): 원문에 명시적으로 가능하면 true, 명시적으로 불가하면 false, 언급이 없거나 모호하면 null(보수적 판정). 원문은 `raw`에 보존하고, `evidence`는 `raw`와 `source_id`로 만든다.
  - **하드 제약 판정은 항목별로 한다**: `WHEELCHAIR` → `wheelchair = true`만 통과, `STROLLER` → `stroller = true`만 통과. null은 기본 후보에서 제외하고 "정보 없는 장소 포함" 제안 대상(FR-013)으로 둔다. false는 제외한다.
  - **등급은 표시용 요약**이다(휠체어·유모차 두 항목 기준, DEC-026으로 보완): 둘 중 하나라도 true → `VERIFIED`, true 없이 false가 하나라도 있으면 → `UNSUITABLE`, 둘 다 정보 없음 → `UNKNOWN`. 등급만으로 하드 제약을 판정하지 않는다.
- 이유: 등급 하나로 판정하면 "유모차는 되지만 휠체어는 안 되는 장소"가 휠체어 사용자에게 추천될 수 있다. 계약이 이미 항목 4개를 갖고 있다.
- 영향: FR-008, FR-013, FR-018, AI-REQ-05, NFR-009

  1. 이동시간 계산 시 보행 속도를 낮춘다. **초기값: 일반 4km/h → 부상 3km/h**

  3. 계단 회피(HARD)는 장소 단위로 `wheelchair = true`를 대리 지표로 판정한다. null은 `UNKNOWN`(FR-013 제안 대상), false는 제외.
  4. 이동 경로의 계단·경사는 데이터가 없어 확인할 수 없으므로, 코스 `warnings`에 확인하지 못했다고 알린다.
  5. 장소 수를 줄이고 체류를 늘리는 쪽으로 점수를 준다(SOFT).

  - **수치 확인 (2026-11-20, 이찬용 제안 → PM 확인)**: 해운대 실제 데이터(직선거리 기준)로 10분과 15분을 비교했다. 10분이면 동백섬 쪽에서 3~5곳 코스가 나오고(3곳 이상 39개) 아쿠아리움·해리단길은 들어가지 않는다. 15분이면 시가지까지 이어져 170개로 늘어난다. **10분·3 km/h를 유지한다.** 직선거리 추정이라 실제 보행은 더 길고(돌아가는 길), 부상은 하드 조건이라 코스 수를 늘리려고 기준을 완화하지 않는다. 대신 부상 안내 경고에 **"이동이 힘들면 택시·대중교통 이용을 권해요"**를 함께 표시한다(문구만 추가, 계약 변경 없음). 대중교통 연계는 향후 과제(DEC-028)로 발표한다.

## DEC-020 이동제약 사용자 선택 우선
- 날짜: 2026-11-09 · 결정자: 김세민(PM) · 계기: 이슈 #6 정할 것 2, PR #13 제안 2 (승인 + 경고 추가)
- 결정: PR #13 제안 2를 그대로 승인한다.
  - 이동제약이 null/UNSET이고 영유아 동반이면 `[STROLLER]`/HARD/DEFAULT (DEC-002).
  - **`source=USER`인 이동제약이 우선**한다. USER의 `[]`(제약 없음)는 유지하고, USER의 비어 있지 않은 목록에도 유모차를 자동 추가하지 않는다.
  - 카드에서 유모차만 해제하면 다른 제약은 유지하고 USER로 저장한다. 해제 상태는 이후 대화에서 자동 재적용하지 않는다. 사용자가 유모차를 명시적으로 요청하면 USER/HARD로 추가한다.
  - 이동제약을 null/UNSET으로 초기화하면(명시적 `[]`와 구분) 영유아 동반 시 기본값 적용 대상으로 돌아간다. 영유아 동반을 취소하면 DEFAULT로 들어간 유모차만 제거한다.
  - **추가:** 사용자가 고른 이동제약 목록에 유모차가 없는데 영유아 동반이면, 응답 `warnings`에 "유모차 조건은 자동으로 넣지 않았어요. 필요하면 조건 카드에서 추가해 주세요."를 붙인다. 질문이 아니므로 질문 한도를 쓰지 않는다.
- 이유: 이동제약의 출처(source)는 목록 전체에 하나라 USER와 DEFAULT를 섞을 수 없다. 다만 부상(INJURY)과 영유아 동반이 겹치면 유모차 조건이 빠진 것을 사용자가 모를 수 있어, 하드 제약을 몰래 완화하지 않도록 경고로 알린다.
- 영향: FR-005, FR-006, FR-018, DEC-002

  - 질문 뒤 다음 메시지에서도 영유아 여부를 답하지 않으면 다시 묻지 않고 `hasInfant=false`로 보며, `warnings`(`UNCONFIRMED_CHANGE`)로 "영유아 동반이면 조건 카드에서 바꿔 주세요."를 알린다.
  - **인원 수는 묻지 않는다.** 혼자는 1, 연인은 2로 본다. 그 밖에 인원을 모르면 동행 항목을 저장하지 않고(UNSET) 질문하지 않는다. 동행은 소프트 조건이라 코스 생성을 막지 않는다. 계약의 `count` 필수는 바꾸지 않는다.
- 이유: 영유아 동반은 가족에서 흔하고 유모차 하드 제약으로 이어져, 묻지 않고 "없음"으로 두면 유모차로 갈 수 없는 코스가 나올 수 있다. 친구·연인에게까지 묻는 것은 질문 한도만 쓰고 결과는 거의 바뀌지 않는다. 질문을 한 번으로 제한해 대화가 막히지 않게 한다.
- 영향: FR-002, FR-004, FR-018, AI-REQ-06, DEC-002, DEC-021

## DEC-024 여러 수정 요청은 하나씩 처리

## DEC-025 조건을 바꾸는 요청은 조건 변경 경로로
- 날짜: 2026-11-16 · 결정자: 김세민(PM) · 계기: 수정 요청 평가셋 Q3 (PR #53)
- 문제: 코스를 본 뒤 "저녁 7시까지로 늘려줘"처럼 장소가 아니라 조건(시간창 등)을 바꾸는 요청은 ChangeOp 5종에 없다. 특정 장소의 체류 늘리기로 잘못 해석될 수 있다.
- 결정:
  - 수정 해석이 조건 변경 요청을 알아보면 ChangeOp를 만들지 않고 **조건 변경으로 분류**한다. 시스템은 기존 채팅·조건 카드 경로(조건 추출·정책, #48)로 조건을 고치고 "종료 시각을 7시로 바꿨어요. 코스를 다시 만들까요?"처럼 **코스 재생성**을 안내한다.
  - 구분 기준: 시간·지역·이동수단·이동제약·예산·제외 카테고리 등 **조건 자체**를 바꾸는 말은 조건 변경, 특정 장소(번호·이름·카테고리)를 가리키는 말은 장소 수정(ChangeOp)이다.

  - 조건 변경 뒤 재생성은 "나머지 유지"(AC-007) 대상이 아니다. AC-007은 장소 수정에만 적용한다.
- 이유: 조건 저장·revision·검증 규칙을 한 곳(채팅·카드)에만 두어 안전하다. 조건이 바뀌면 후보 자체가 달라지므로 재생성이 맞다. 새 연산을 만들지 않아 구현량이 줄어든다.

## DEC-026 무장애 문장 판정 규칙과 등급 보완
- 날짜: 2026-11-17 · 결정자: 김세민(PM) · 계기: 이찬용 무장애 판정 규칙 초안(PR #45 제안 3, 미결 항목 11/16)

  1. **판정 방향 (이찬용 초안 승인)**: 무장애 응답은 자유 문장이다. 빈 값은 null, **승인된 표현 목록**에 맞는 문장만 true/false로 판정한다. 같은 항목에서 문장끼리 충돌하면 null로 두고 검토 대상으로 기록한다.
  - **원본 항목 구분**: TourAPI 무장애 응답(`detailWithTour2`)의 `wheelchair` 항목은 휠체어 **대여** 여부라 우리 DB·API의 `wheelchair`(휠체어 접근 가능) 판정에 쓰지 않는다. 원본의 `stroller` 항목도 해운대 수집 결과 값 18개가 모두 대여 정보로 확인되어(11/19, PR #64) 판정에 쓰지 않는다. 휠체어·유모차 값은 출입 통로·경로·엘리베이터·화장실 등 다른 원본 항목의 문장으로 판정한다. 원본 항목별 매핑은 표현 목록과 함께 확정한다.
  2. **표현 목록 확정**: 해운대 전체 수집 후 이찬용이 true/false 표현 목록을 만들고 PM이 확인한다(기한 11/20). 목록이 사실상 하드 제약 판정 기준이기 때문이다.
  3. **등급 보완 (DEC-015)**: 등급은 **휠체어·유모차 두 항목만** 본다(엘리베이터·장애인 화장실은 등급에 넣지 않는다). 두 항목 중 true가 하나라도 있으면 `VERIFIED`, true 없이 false가 하나라도 있으면 `UNSUITABLE`(예: 휠체어 false·유모차 null), 둘 다 null이면 `UNKNOWN`. 등급은 표시용이고 하드 판정은 DEC-015대로 항목값으로 한다. 장소 상세 화면은 등급과 함께 항목별 값을 표시한다.
  4. **SRS 문구**: FR-008·표 3-1·AC-004의 "확인됨만 후보"를 항목값 기준으로 고친다.
  5. **후보 수 보고**: 수집 후 휠체어·유모차 각각의 true·false·null·충돌 건수와 두 서비스 ID 매칭률을 바로 보고한다(11/20). 너무 적으면 정보 없음 장소 포함(FR-013)을 앞당길지 PM이 정한다.
- 이유: 알려진 불가 정보를 정보 없음으로 표시하면 사용자가 주의할 기회를 잃는다. 대여 필드를 접근성으로 쓰면 잘못된 true가 생긴다.

## DEC-027 체류 연장 시 뒤 장소 시각 이동 허용 (AC-007 예외)
- 날짜: 2026-11-17 · 결정자: 김세민(PM) · 계기: PR #53 김영무 리뷰(AD-09 체류 연장과 AC-007 충돌)

- 이유: 체류를 늘리면 뒤 일정이 밀리는 것이 사용자가 기대하는 동작이다. 장소·순서를 유지하므로 "코스를 멋대로 바꾸지 않는다"는 AC-007의 취지를 지킨다.

## DEC-033 정보 없는 장소 포함(FR-013) 제출본 범위
- 날짜: 2026-11-22 · 결정자: 김세민(PM) · 계기: 김영무 범위 정리 제안(11/22). 구현 #72·#78
- 결정:
  - 이동제약에 필요한 접근성 정보가 없는(null) 장소 때문에 제외된 장소가 있으면 포함 재생성을 제안한다. 코스가 나온 뒤뿐 아니라 **후보 부족으로 코스가 나오지 않을 때도** 제안한다(FR-013보다 넓게, 사용자에게 유리).
  - 사용자가 확인창에서 **명시적으로 수락한 경우에만** 포함한다. 초기 동의는 false이며 자동으로 동의하지 않는다.
  - 포함한 코스는 `validation.status`를 **PASSED가 아니라 CONDITIONAL**로 표시하고, 조건부 코스 안내와 해당 장소별 경고(`UNKNOWN_ACCESSIBILITY_INCLUDED`, `placeIds`)를 보여 준다. null을 true로 바꾸지 않는다.
  - 접근성 null만 포함 대상이다. 운영시간 누락·접근 불가(false)·반경 밖·사후면세점·제외 카테고리는 계속 제외하고, 부상 구간당 10분 제한도 유지한다(DEC-015·016·023).
  - 이동제약 값이 실제로 바뀌면 동의를 초기화하고 다시 묻는다(목록 순서·출처만 바뀌면 유지). 동의 저장에 실패하면 재생성을 중단하고, 코스 생성만 실패하면 저장된 조건으로 다시 시도한다.
- 이유: 무장애 정보가 있는 장소가 적어(해운대 53/275, 광안리 휠체어 후보 3곳) 이동제약 코스가 자주 부족하다. 사용자가 알고 선택한 경우에만 정보 없는 장소를 넣고, 확인하지 못한 조건이 있는 코스를 통과로 표시하지 않는다.
- 영향: FR-013, FR-014 ②, AC-006, DEC-015, DEC-021, DEC-026

  - [x] 구현 (김영무 #72, 배진호 #78)

## DEC-034 날씨 판정 기준 (FR-016)
- 날짜: 2026-11-24 · 결정자: 김세민(PM) · 계기: PR #87(이찬용, #33 A단계) 결정 요청
- 결정:
  1. **판정 기준**(설정값, `config/weather.json`)
     | 조건 | 판정 |
     |---|---|
     | 강수확률 ≥ 60% | 실외 **제외** (HARD) |
     | 폭염·한파·호우·대설·태풍 특보 발효 중 | 실외 **제외** (HARD) |

  3. **특보 구역**: 부산 육상 특보구역 코드를 확인하지 못해, 이름이 "부산"으로 시작하고 해상이 아닌 구역의 특보를 4개 권역 모두에 적용한다(보수적).
  4. **실외 판정**: DB의 실내·실외 값이 630곳 모두 비어 있어, TourAPI 분류 코드로 **확실한 실외**(자연관광·도시공원·골목길/문화거리·다리)만 `OUTDOOR`로 본다. **먹자골목 3곳**(부평족발골목·자갈치 양곱창 골목·서면먹자골목)은 활동이 식당 안이라 실외에서 뺀다.
  5. 판단이 애매한 44곳(시장·전망대 등)과 나머지 "모름" 장소는 **제외도 감점도 하지 않는다**(정보 없음을 실외로 바꾸지 않음). 코스 연결 시 "실내·실외 정보가 없는 장소는 날씨를 반영하지 않았어요" 경고를 붙인다.

## DEC-035 장소 바꾸기(REPLACE)의 시간 처리
- 날짜: 2026-11-24 · 결정자: 김세민(PM) · 계기: PR #86(김영무) 미합의 항목 "장소 교체 후 시각 조정"
- 결정:
  - `REPLACE`는 **대상의 시작·종료 시각과 체류시간을 그대로 두고**, 그 시간대에 영업하며 앞뒤 장소와의 이동시간이 기존 틈에 맞는 후보로만 교체한다. 나머지 장소·순서·시각은 바꾸지 않는다(AC-007).
  - 새 장소의 기본 체류시간이 달라도 원래 시간대를 쓴다. 더 머무르고 싶으면 이어서 "체류 늘리기"(DEC-027)로 뒤 일정만 민다.
  - 맞는 후보가 없으면 **코스를 바꾸지 않고**(NOT_APPLIED) 이유와 대안(빼기·체류 늘리기 등)을 안내한다. 조건을 완화해 다른 후보를 넣지 않는다.
- 이유: 이미 구현된 방식(#86)이라 남은 일정에 부담이 없고, "1번만 바꿨는데 나머지 시간이 바뀌는" 혼란이 없다. 새 장소에 맞춘 재배치(체류시간 반영·전체 재배치)는 AC-007 예외가 더 필요하고 작업량이 크다.
- 영향: FR-015, AC-007, UC-005, DEC-024, DEC-027
- 반영 위치:
  - [x] 서버 구현 (김영무, #86)
  - [ ] 화면에서 미적용 이유·대안 안내 (배진호, #89)

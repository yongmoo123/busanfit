## 1. 프로젝트 개요

### 1.1 배경

부산은 바다·문화·음식 등 놀거리가 많지만, 대부분의 코스 추천은 "건강한 성인이 대중교통으로 하루를 통째로 쓴다"는 일반 사용자를 가정한다. 한편 부산교통공사·한국관광공사·부산시는 역사 엘리베이터, 무장애 관광지, 주차장 운영시간 등 실제 제약을 판단할 수 있는 공공데이터를 개방하고 있다.

### 1.2 문제 정의

- 휠체어·유모차 이용자, 부상자는 일반 추천 코스를 그대로 따를 수 없다(계단, 긴 도보, 엘리베이터 없는 역).

- 영화·예약 식당 등 고정 일정이 있으면 그 사이 공백 시간을 어떻게 채울지 스스로 조사해야 한다.

- 자차/대중교통, 예산, 날씨, 동행자(연인·가족·친구)에 따라 적합한 코스가 달라지지만, 이를 한 번에 반영하는 서비스가 없다.

- 범용 LLM에 물어보면 존재하지 않거나 폐업한 장소, 실제로 접근할 수 없는 장소를 추천할 수 있다.

### 1.3 목표

1.  자연어 대화에서 사용자 제약을 구조화하고, 하드/소프트 제약으로 구분한다.

2.  부산 공공데이터에 실제로 존재하는 장소만으로, 하드 제약 위반 0%인 코스를 생성한다.

3.  기본값으로 첫 코스를 빠르게 보여주고, 후속 질문과 대화형 수정으로 사용자가 자연스럽게 코스를 조정하도록 유도한다.

4.  모든 추천 장소에 데이터 출처와 접근성 등급을 표시한다.

## 2. 기존 서비스 대비 차별점

부산핏의 핵심 차별점은 "LLM은 이해와 설명, 계산은 규칙 엔진"이라는 역할 분리로, 제약을 지키는 코스를 재현 가능하게 만든다는 점이다.

| 구분 | 지도 앱 장소 검색 | 여행 일정 앱 | 범용 LLM 챗봇 | 부산핏 |
|----|----|----|----|----|
| 자연어 조건 입력 | 키워드 위주 | 수동 편집 | 가능 | 가능 |
| 이동제약(휠체어·유모차·부상) 반영 | 제한적 | 없음 | 불확실 | 하드 제약 필터 |
| 시간창·이동시간 계산 | 경로 단위 | 사용자 몫 | 부정확 | 스케줄러가 계산 |
| 장소 실존 보장 | 보장 | 보장 | 환각 가능 | DB 검증 후 출력 |
| 데이터 출처 표시 | 일부 | 일부 | 없음 | 장소별 표시 |
| 대화형 부분 수정 | 없음 | 없음 | 전체 재생성 | 해당 부분만 재계산 |

단순 LLM 호출만으로 구성된 시스템이 아니라, 제약 추출 → 필터 → 점수화 → 스케줄링 → 검증 → 설명의 다단계 파이프라인으로 동작한다.

## 3. 개발 범위

구현 범위는 비로그인 반응형 웹에서의 제약 분석·코스 생성·대화형 조정이며, AI는 LLM만 사용한다.

### 3.1 포함

- 채팅 기반 조건 입력 및 제약 프로필 추출: 시간, 이동능력(자차·대중교통·장애요소), 예산, 선호도(관광·체험·야외활동 등), 날씨, 동행 관계(연인·가족·친구)

- 하드/소프트 제약 구분 및 기본값 적용

- 제약 기반 후보 검색, 시간·이동시간을 고려한 코스 생성

- 코스 타임라인 + 카카오맵 표시, 장소별 추천 이유·출처·접근성 등급

- 후속 조정 제안(최대 3개) 및 대화형 부분 수정

- 자차 모드 주차장, 역사 엘리베이터·보관함 등 편의시설 표시

### 3.2 제외

- 예약·결제, 회원가입·로그인

- 실시간 혼잡도, 실시간 영업 여부 보장

- 영화관 상영시간표 연동(공개 API 없음 → 사용자가 고정 일정으로 직접 입력)

- 쓰레기통·휴대폰 충전소 안내(부산 공개 데이터 미존재)

- 이미지 기반 질의(VLM): 향후 확장 항목으로만 기술

- 부산 외 지역

### 3.3 지역 범위

부산 전역 데이터를 수집하되, 추천 품질 검증과 시연은 주요 권역(서면, 해운대, 광안리, 남포)에 집중한다.

### 3.4 향후 확장 가능성

- VLM을 활용한 "이런 분위기 장소" 사진 질의

- 대중교통 경로 API 연동을 통한 이동시간 정밀화

- 식이 제한(채식·알레르기) 데이터 연동

## 4. 핵심 기능

과제 필수조건(핵심 기능 3개 이상)을 다섯 가지 기능으로 충족한다.

| 번호 | 기능 | 내용 | 과제 예시 대응 |
|----|----|----|----|
| F1 | 대화형 제약 분석 | LLM이 채팅에서 제약 프로필(JSON)을 추출하고 하드/소프트를 태깅, 필수 정보 누락 시 최대 2개 되물기 | 사용자 맞춤 |
| F2 | 제약 기반 장소 검색 | 공공데이터 DB에서 하드 제약을 만족하는 후보만 조회, 접근성 등급(확인됨/정보 없음/부적합) 부여 | 데이터 검색 |
| F3 | 맞춤 코스 생성 | 소프트 제약 점수화 + 시간창·이동시간·체류시간 기반 스케줄링, 고정 일정 사이 공백 채우기, 검증 후 출력 | 사용자 맞춤 추천 |
| F4 | 지도·동선 시각화 | 타임라인과 카카오맵 동선, 장소 상세·출처, 주변 편의시설(주차장·엘리베이터·보관함) | 지도/위치 연동 |
| F5 | 상호작용 코스 조정 | 기본값으로 첫 코스 생성 후 조정 제안 칩 표시, 칩·자연어 수정 시 해당 부분만 재계산 | 사용자 맞춤 |

### 4.1 기본값 정책

| 항목 | 기본값 | 후속 질문 예시 |
|----|----|----|
| 카페 체류 | 60분 | "카페에 더 오래 있을 예정이신가요?" |
| 식사 체류 | 70분 | "식사는 여유있게 하실건가요?" |
| 전시·문화시설 체류 | 시설별 관람소요시간, 없으면 60분 | "전시는 얼마나 보실 예정인가요?" |
| 접근성 정보 없는 장소 | 이동제약 모드에서 제외 | "정보가 없는 장소도 포함해서 다시 만들어드릴까요?" |
| 미입력 이동수단 | 대중교통 | "자차로 이동하시나요?" |
| 미입력 예산 | 제한 없음, 가격대 보통 | "예산 상한이 있으신가요?" |

화면에는 기본값이 적용된 항목을 표시하고, 코스 생성 후 기본값 적용 항목·정보 없음으로 제외된 장소·날씨 리스크 순으로 조정 제안을 띄운다.

## 6. 기술 스택 및 LLM 선정

프론트엔드는 React, 백엔드는 FastAPI, LLM은 개발 단계 Gemini Flash 무료 티어 후 시연 단계 유료 소형 모델로 전환한다.

| 영역 | 선택 | 이유 |
|----|----|----|
| 프론트엔드 | React(또는 Next.js) + 카카오맵 JavaScript API | 반응형 웹, 국내 지도 표시 |
| 백엔드 | Python FastAPI | 데이터 처리·LLM 연동 라이브러리 풍부 |
| DB | SQLite (DEC-005) | 좌표 기반 반경 검색을 애플리케이션에서 계산, 설치 없이 로컬·CI·배포 환경이 같음 |
| LLM | 개발: Gemini Flash 계열(무료 티어) / 시연·최종: 유료 소형 모델(Claude Haiku 5.5 또는 GPT-5 mini) | 비용 최소화, AIService 추상화로 교체 가능 |
| 협업·배포 | GitHub, GitHub Actions | 과제 필수조건, 자동 빌드·테스트 |

### 6.1 LLM 비교

| 후보 | 장점 | 단점 |
|----|----|----|
| Gemini Flash 무료 티어 | 결제수단 없이 무료, 만료 없음 | 분당 요청 제한 낮음, 무료 티어 입출력이 모델 개선에 사용될 수 있음 |
| Claude Haiku 5.5 | 입력 100만 토큰당 \$0.10, 출력 \$0.50(10만 토큰 이하 프롬프트) | 결제수단 필요, 2026-10 출시로 자료 적음 |
| GPT-5 mini | 입력 \$0.25, 출력 \$2.00, 국내 자료 풍부 | 결제수단 필요 |
| 로컬 모델(Ollama 등) | 무료, 데이터 외부 미전송 | 한국어 JSON 추출 품질 불안정, GPU 서버 필요 |

코스 1회당 LLM 호출은 3~5회로, 유료 소형 모델도 학기 전체 비용이 수천 원 수준이다. 부상·장애 정보를 다루므로 무료 티어 개발 중에는 가상 시나리오만 사용한다. (가격은 2026-10 기준, 변동 가능)

## 7. 개발 프로세스 및 GitHub 운영

요구사항·설계는 중간발표 전에 문서화하고, 구현은 2주 단위 반복적·점진적 모델로 진행한다.

### 7.1 개발 프로세스

1.  요구사항 분석: SRS 작성(기능·비기능·AI 요구사항, 유스케이스)

2.  아키텍처·상세 설계: SDD 작성(아키텍처, 컴포넌트, UML, DB, API)

3.  구현: 스프린트별로 Must → Should → Could 순서

4.  테스트: 단위·통합 테스트 + AI 평가 테스트셋(제약 추출 문장 30개, 수정 요청 20개, 코스 시나리오 10개)

5.  인수 테스트 및 최종 발표

### 7.2 GitHub 운영 규칙

- 브랜치: main(배포) / develop(통합) / feature/\<기능명\>

- PR: develop으로만 병합, 팀원 1명 이상 리뷰 승인 필수

- 이슈: 요구사항 ID(FR-xxx)를 이슈·커밋 메시지에 명시해 추적성 확보

- 자동화: GitHub Actions로 PR 시 빌드·테스트 자동 실행

- 보안: API 키는 환경변수·GitHub Secrets로 관리, 저장소에 커밋 금지

- 문서: 계획서·SRS·SDD를 docs/ 폴더에 버전별로 보관

## 10. 위험 관리

가장 큰 위험은 공공데이터의 빈 항목과 LLM 환각이며, 각각 "정보 없음" 등급과 DB 검증 단계로 대응한다.

| 위험 | 영향 | 대응 |
|----|----|----|
| 무장애·가격·영업시간 데이터 부족 | 후보 감소, 제약 판단 불가 | "정보 없음" 등급 표시, 제외 후 포함 재생성 제안, 하드 제약은 데이터가 있는 장소에만 적용 |
| LLM 환각(존재하지 않는 장소) | 잘못된 추천 | LLM은 장소를 생성하지 않고 DB 후보 중에서만 선택, CourseValidator가 실존 여부 검증 |
| 외부 API 호출 한도·장애 | 응답 실패 | 공공데이터 배치 수집 후 DB 캐싱, LLM 실패 시 재시도 1회 후 규칙 기반 대체 |
| 무료 티어 데이터 정책 | 민감정보 외부 활용 가능성 | 개발 중 가상 시나리오만 사용, 시연 시 유료 API 전환 |
| 이동시간 추정 오차 | 코스 시간 어긋남 | 장소 간 여유시간(버퍼) 반영, 역간 표준 시간 기준임을 고지 |
| 일정 지연 | 기능 미완성 | Could → Should 순으로 범위 축소, Must 기능 우선 완성 |
| 프론트엔드 작업량 집중(1명) | UI 지연 | PM이 와이어프레임·테스트 분담, 지도는 카카오맵 기본 컴포넌트 활용 |
